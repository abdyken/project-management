# T3.2 — Retrieval index

- **Story:** US3
- **Est.:** 5 ч
- **Зависит от:** T3.1 (FAQ base, Askhat), T0.7
- **Приоритет:** P2 — core
- **DoD (из спринта):** индекс строится из чистого состояния одной командой; ручная проверка 5 вопросов возвращает ожидаемый FAQ-пункт первым.
- **Статус: реализовано и проверено, ждёт T3.1.** Работают оба бэкенда — файловый (офлайн-разработка) и Postgres/pgvector (подтверждённый стек T0.1) — на демо-данных вместо реального T3.1. Код: [`app/assistant/retrieval.py`](../../app/assistant/retrieval.py) (файловый + keyword fallback), [`app/assistant/retrieval_pg.py`](../../app/assistant/retrieval_pg.py) (pgvector), миграция [`migrations/versions/0001_create_faq_embeddings.py`](../../migrations/versions/0001_create_faq_embeddings.py). 5 тестовых вопросов — [`tests/test_retrieval.py`](../../tests/test_retrieval.py), все проходят.

## Что нужно сделать

Построить индекс поиска по FAQ-базе (эмбеддинги + keyword fallback) и скрипт reindex, который можно перезапускать при обновлении FAQ приёмной комиссией.

## План реализации

1. Дождаться выгрузки от T3.1 (Askhat): JSON/CSV с полями `question, answer, category, source_link, last_update`, ~30 записей, прошедшие ревью Serdar перед индексацией (это явно указано в DoD задачи T3.1).
2. **Embedding-индекс:** для каждого FAQ-пункта считается вектор эмбеддинга (провайдер из T0.7) по тексту вопроса. Подтверждено T0.1: БД — Postgres 16 + pgvector, эмбеддинги хранятся в таблице `faq_embeddings` (колонка `Vector(256)`, ширина = размерность mock-провайдера; при переходе на реальный провайдер с другой размерностью — обновить `EMBEDDING_DIMENSIONS` в `app/assistant/models.py` и накатить новую миграцию, pgvector требует фиксированную ширину). Файловый JSON-бэкенд (`INDEX_BACKEND=file`) остаётся как офлайн-режим для разработки и юнит-тестов без поднятия БД.
3. **Keyword fallback:** TF-IDF cosine поверх `question + answer`, реализован вручную на `numpy` (без внешней зависимости типа `rank-bm25`) — подстраховка на случай, если эмбеддинг-провайдер недоступен (`ProviderError`) или неоднозначен.
4. **Similarity scoring:** основной сигнал — косинусная близость эмбеддингов (в pgvector — через `cosine_distance()`); keyword-скор — как единственный сигнал при недоступном embedding-провайдере (fallback перехватывается автоматически в `RetrievalIndex.search` / `PgRetrievalIndex.search`).
5. **Reindex-скрипт:** `python scripts/reindex_faq.py` — идемпотентный, полная пересборка (DELETE + INSERT для Postgres, перезапись файла для file-бэкенда). Проверено на реальном Postgres 16 + pgvector (Docker) — миграция и reindex отработали, результаты поиска через SQL идентичны файловому бэкенду (расхождение в score на уровне float-погрешности).
6. **Ручная проверка:** 5 вопросов из DoD — см. `tests/test_retrieval.py`, все возвращают ожидаемый FAQ-пункт первым (запускается автоматически в CI через `pytest`, не только вручную).

## Что нужно от других

- **T3.1 (Askhat):** финальный экспорт FAQ-базы — сейчас используется демо-заглушка `app/data/faq_sample.json` (12 пунктов) вместо реальных ~30. Формат (`faq_id, question, answer, category, source_link, last_update`) уже совпадает с ожидаемым от T3.1 — просто заменить файл и прогнать `reindex_faq.py`.
- **T0.5 (Nurmek):** реальная Postgres-БД дев-окружения — сейчас `INDEX_BACKEND=postgres` проверен только на локальном Docker-контейнере (`docker run ... pgvector/pgvector:pg16`, команда в `backend/README.md`), не на деплое.
